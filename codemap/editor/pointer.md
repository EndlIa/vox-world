# src/editor/pointer.ts

Ring: 3 · Layer: editor · Depends on: document/project.ts, editor/session.ts, editor/ops.ts, three-runtime/picking.ts, three-runtime/overlay.ts, voxels/uniform/grid.ts, voxels/uniform/region.ts, three

## Responsibility
All pointer handling in the viewport, in one place: point pick (cell or object), the region a press names, and the commit of the active tool. It translates pointer events into session state and `editor/ops.ts` calls. It never mutates voxel data, never renders, and never owns navigation — `OrbitControls` owns that.

## Public interface
```ts
import type { ObjectId, Project } from '../document/project.js';
import type { EditorSession, SelectionShape } from './session.js';
import type { EditHistory } from './history.js';
import type { Picker } from '../three-runtime/picking.js';
import type { Overlay } from '../three-runtime/overlay.js';
import type { HexColor, IntBox3 } from '../voxels/uniform/grid.js';
import { regionBounds } from '../voxels/uniform/region.js';
import type { RegionShape } from '../voxels/uniform/region.js';
import type * as THREE from 'three';

type PointerCallbacks = {
  onSessionChange(): void;      // selection or tool changed
  onProjectChange(ids: readonly ObjectId[]): void;
                                // the objects an operation wrote, so the caller can rebuild
                                // exactly their derived geometry
};

class PointerTool {
  constructor(opts: { dom: HTMLElement; project: Project; session: EditorSession;
    picker: Picker; overlay: Overlay; getCamera: () => THREE.PerspectiveCamera;
    getGizmoBusy: () => boolean; history: EditHistory; callbacks: PointerCallbacks });
                                // the stack each press records one step in
  detachSelection(): void;      // commits a detach on the region the session already selected
  dispose(): void;
}
```

`getGizmoBusy` is the gizmo's claim on the pointer (`ViewportControls.gizmoBusy()` in `app/main.ts`): the tool defers a left press exactly when it answers `true`, and takes the press itself otherwise. `detachSelection()` is the tool's one operation that is not a press: it runs the `detach` the panel's button asks for on the current selection (see Internal logic 10).

## Internal logic
1. The constructor stores the seven arguments — `getCamera`, the closure that names the app-owned `PerspectiveCamera`, and `getGizmoBusy`, the closure that reports whether the gizmo owns the pointer — plus private drag state (one `DragState`: `pointerId`, `objectId`, `cell`, `anchorCell`, `cornerCell`, `outer`, `dragging`, `plane`, `normal`, `toLocal`) and the `pressActive` flag, and adds `pointerdown`/`pointermove` on `dom` and `pointerup`/`pointercancel` on `window`, so a drag that leaves the canvas still ends. It touches no `dom.style` and no controls state.
2. NDC from an event: `x = (clientX - rect.left) / rect.width * 2 - 1`, `y = -((clientY - rect.top) / rect.height * 2 - 1)` with `dom.getBoundingClientRect()`, so picking matches what the canvas shows at any CSS size. Every pick then passes that NDC *and* `getCamera()` to the picker, resolved for that one call: the closure names the app-owned viewport camera — the one navigation moves — so a pick is computed against that camera and no other.
3. Only button 0 starts an edit. `OrbitControls` is configured `LEFT: null` (middle rotates, right pans, wheel zooms), so no left drag is navigation; buttons 1 and 2 return immediately without `preventDefault()` and without touching state.
4. Gizmo precedence: a left press belongs to the gizmo exactly when `getGizmoBusy()` answers `true` — `ViewportControls.gizmoBusy()` reports `TransformControls.dragging` and a non-null hovered `axis` for each handle set the attached subject holds, so it is true for a drag in progress and for a pointer resting on a handle of any of them, and false before any attachment or for a set that is disabled. Pointer capture is deliberately *not* consulted: `TransformControls` calls `setPointerCapture` on the shared `dom` element on **every** press, whether or not a handle was hit, so `dom.hasPointerCapture(event.pointerId)` — and `defaultPrevented` with it — says nothing about which layer owns the gesture, and treating it as a claim would swallow every press and make cell selection unreachable. A gesture of the gizmo's is bracketed by `ViewportControls.onGizmoChange` during the drag and `onGizmoCommit` once on pointer-up, with the mirrored node already holding the dragged transform in between; `app/main.ts` wires that commit to `ops.setTransformFromWorldMatrix` and marks the object dirty, which is why this file does not import `controls.ts`.
5. `pointerdown` (button 0, unclaimed) picks with `picker.pick(ndc, this.getCamera())`. No hit clears the selection to `{ kind: 'none' }`, clears the overlay, and calls `onSessionChange()`. A hit makes the object active, then maps the hit to the region the session's shape asks for: `'cell'` (uniform) → `pressShape(session.selectionShape, dragBox(hit.cell, hit.cell, outer, false, session.addHeight), hit.cell, hit.color)`, which is a box of one cell per click, or the colour group or the island that picked cell names; `'object'` (an imported raw mesh on layer 2) → `{ kind: 'none' }`, because the mesh has no cells to name yet and activating its object is the whole press. The object arm drops any armed drag, paints nothing, and returns before the commit path, so a press on a raw mesh can never act as a cell edit. `outer` is computed once, by `outerCell(session.activeTool, hit.normal)`, and the cell arm then arms the drag with that same hit and step — `armDrag(event.pointerId, hit, outer)` — so no second pick of the same pointer position can disagree with the cell the press already selected and made active, and the box the press previews is the box the release commits. `onSessionChange()` follows a changed selection.
6. Box drag arming, in `edit` mode only, consumes the press's own hit: `armDrag(pointerId, hit: Extract<PickHit, { kind: 'cell' }>, outer)` returns unless the active tool is in `BOX_TOOLS`, the `Record<ActiveTool, boolean>` that lists exactly the four box tools — `select`, `add`, `paint`, `remove` — and unless the session's shape is `'box'`, because a colour group and an island are named by the cell the press landed on and a drag has nothing to extend. A detach is not in that table either: it is a command on the region the selection already holds, it arrives as `commit('detach')` from `detachSelection()` rather than as an armable tool, and so it can never be left armed for the next press. The one payload lookup is `project.get(hit.objectId)?.uniform`, and it returns early when that is `undefined`: a group and an import with no voxel payload have no cells to address, so the point selection stands. The anchor is `hit.cell` itself — the exact cell the instance lookup named — so a press on a face addresses the cell the user sees rather than the one past that face, which is what flooring the hit's own surface point would name, since the raycast reports a point on the face's plane. `outer` — `outerCell(session.activeTool, hit.normal)` — is `[0, 0, 0]` for every tool but `add`, whose box is stepped out of the pressed face by `dragBox`: the normal's dominant axis, one cell into the empty layer the face opens onto, and still `[0, 0, 0]` when the raycast reported no face, because a hit with no face has no outward direction to step in. The drag plane is built from that face: its world normal is `hit.normal` through the object's `Matrix3.getNormalMatrix`, normalized, or — when the raycast reported no face — the camera's view direction negated, the direction the ray travels; the plane passes through `hit.point`. The drag stores that face normal in the object's own frame (`hit.normal?.clone()`), the step, and `toLocal: worldMatrix.invert()`, keeps `cell` as the object's own `grid.cellSize`, starts both corners at `hit.cell`, and starts `dragging` false, which is what keeps a press that never moves a one-cell edit whatever the wall height says.
7. Drag tracking: each tracked `pointermove` picks with `picker.pick(ndc, this.getCamera())` — the same single call the press used, and the only pick the tool makes, because a hit already names the cell the user sees. A `'cell'` hit on the anchor object sets `cornerCell` to exactly the cell it named. Any other answer — a miss, or a hit on another object — keeps the gesture in the plane stored at the press: `_ray.setFromCamera`, `ray.intersectPlane(drag.plane, _planeHit)`, that world point through `toLocal`, half a cell back along `drag.normal` when there is one (a plane point lies on the face's own plane, so flooring it would land in the cell past the face, while the two axes the drag travels are untouched), and finally `cellOfLocal`, which floors after dividing by the cell — a cell is `1 / subdivision` of the world unit, a power-of-two fraction, so the division is exact — and holds the result inside the packed key space (`KEY_MIN`..`KEY_MAX`), the only range a cell may come from at all. A ray parallel to the plane leaves the corner where it was. The frame is the anchor object's (captured at the press through `toLocal`), so a box can be drawn through empty space — which is how `add` grows a model — and can never jump to another object. The box is `dragBox(anchorCell, cornerCell, drag.outer, drag.dragging, session.addHeight)`: the cells the pick named, stepped by `outer`, normalized so both corners are inclusive, and — once a tracked move has set `dragging` and the session's height is above one — stretched along the outer axis to that many cells, which is the add wall. `dragging` is set here, on the same move that first moves the box. The move allocates nothing: the ray, its plane point, that point in cell space, and the two matrices that turn the pressed face into a world normal are module scratch.
8. Live preview only: each tracked move redraws `overlay.showBox(dragBox(...), project.worldMatrix(drag.objectId), drag.cell)` — the signature is `showBox(boxLocal, matrixWorld, cell, color = DEFAULT_COLOR)`, because the box is expressed in the object's own cells and only that cell size turns it into world units. Nothing is written to the container while the button is down, and nothing is reported as text.
9. Commit on `pointerup`, in `edit` mode only (an `object`-mode press only chose whose gizmo is shown), one operation per press, chosen by the commit verb `commit(tool: CommitVerb = this.session.activeTool)` after the committed region is stored with `session.setSelection` — `dragBox(drag.anchorCell, drag.cornerCell, drag.outer, drag.dragging, session.addHeight)` when the press dragged, and the selection the press already set (the same builder with the click's degenerate corners) when it never moved. The local `type CommitVerb = ActiveTool | 'detach'` is what lets one method serve both: a press never passes a verb, so its verb is always the session's `activeTool`, and the session supplies only `select`, `add`, `paint` and `remove` — only the `detachSelection()` command supplies `detach` (see item 10). The capture is taken before the operation runs and committed after it (`history.begin` on the region the selection names, then `history.commit`), so the step a press leaves behind is the difference the operation actually made. The chain is `select` → the region stays the selection and no voxel is written, `add` → `addRegion(project, objectId, selection.shape, session.editColor)`, `paint` → `paintRegion(project, objectId, selection.shape, session.editColor)`, `remove` → `removeRegion(project, objectId, selection.shape)`, and else (only a commanded detach) → `detachSelection(project, selection)`, which refuses any shape that is not a box with the new object becoming active and the selection reset to `{ kind: 'none' }`. The commit reports the ids an operation wrote: `changed` starts as `[selection.objectId]`, and a `detach` also pushes `result.objectId` where the op reported one, because both halves of a detach change geometry and reporting only the object that gained cells would leave the source drawing cells it no longer holds. Success that wrote cells (`result.cells !== 0`) calls `onProjectChange(changed)` so the mirror rebuilds exactly those objects; a failure changes nothing and logs its literal and detail to the console (`settle`), because the app has no message area left to show them in. The overlay is then cleared and re-shown with the committed selection for tools that keep one, that redraw taking the object's own `uniform.cellSize` for the same reason as the preview. A press with no tracked move commits the degenerate 1×1×1 box, so point add, remove and paint need no separate tool, and a one-cell detach is that box plus the panel's `detach` button. With no box selected the press commits nothing at all.
10. `detachSelection()` is the public command behind the panel's `detach` button: it is `commit('detach')` and nothing else, so it runs the detach on the region `session.selection` already holds — the one verb a press cannot supply, because the session has no `detach` tool (items 6 and 9) — and it ends the way a commit does: the new object active, the region no longer selected, its box gone. The button is a command on the region the `Select` tool chose rather than a tool choice, so it arms no drag and writes no voxel of its own; with the selection at `{ kind: 'none' }` the commit finds nothing to act on and returns, which is why the panel disables the button then.
11. A `pointermove` with no drag in flight draws the hover preview instead of nothing: `preview(ndc)` picks, builds the
    region a press would name with the very same call the press uses (`outerCell` → `dragBox` → `pressShape`, so the
    ghost cannot promise a region the commit would not name), and hands the overlay either its cells or — past
    `GHOST_CELL_LIMIT` cells — the extent that holds them. A press in flight, `object` mode, a tool outside
    `PREVIEW_TOOLS`, a miss, a raw mesh, and a busy gizmo all take the ghost away, because none of them would name a
    region. It writes nothing, changes no selection, and keeps no state: a preview is a drawing, not a step.
12. Every voxel write goes through `editor/ops.ts`. This file never calls `grid.set`, `fillBox`, `clearBox`, `paintBox`, or any other container mutator directly — that is what keeps pointer code from bypassing the budget and the result reporting.
13. `dispose()` removes every listener it added, including the window-level ones, clears the overlay and the drag state, and is idempotent.

## Invariants
- No voxel container is mutated outside `editor/ops.ts`.
- A drag's box always lies in the anchor object's local grid and is inclusive on both corners, and the box a drag previews is the box it commits.
- A press that writes leaves exactly one history step, and a press that changes nothing — a refused operation, a paint over empty space — leaves none, because the operation and the capture are one pair and the history decides what the pair added up to.
- A press names exactly one region of one object, and that region is what the commit acts on: the shape is built once from the pick (`pressShape`) and stored in the session, never re-derived at commit time, so what the overlay frames and what an operation receives cannot disagree.
- A hit-driven corner is exactly the cell the pick named, and the lookup's `cell` is taken verbatim, so a press or a move on a face addresses the cell the user sees and never the neighbour past that face — with one deliberate exception: `add` steps the whole box one cell out of the pressed face, along that face's normal, so its box is the empty layer the face opens onto.
- `add`'s step is `outerCell`: the pressed face's normal's dominant axis, one cell, and `[0, 0, 0]` for every other tool or when the raycast reported no face. No tool but `add` can write a cell the pointer did not name, and `add` only ever writes the layer immediately in front of what it pressed.
- The box `add` previews and commits is later stretched to `session.addHeight` cells along that same axis only when a tracked move happened, so a click is one cell at any height and `paint`, `remove`, and `select` are never stretched: the wall is the add tool's own thickness, not a second box shape.
- A box may leave the anchor object's occupancy — drawing through empty space is how `add` grows a model — but never the packed key space: every plane-derived corner goes through `cellOfLocal` and every stepped cell through `holdCell`, which hold a cell inside `KEY_MIN`..`KEY_MAX`, the only range a cell may come from.
- A move that misses, or hits another object, keeps the box in the anchor object's frame: its corner comes from the plane stored at the press through `toLocal`, the anchor object's world matrix inverted, so the gesture never picks up another object's cells.
- The plane a drag runs in belongs to the pressed face: its normal is that face's normal through the object's normal matrix, or the camera's view direction negated when the raycast reported no face, and a plane point is nudged half a cell back along the face normal because it lies on the face's own plane.
- The drag's cell size is the anchor object's own `uniform.cellSize`, captured at the press, so the nudge, the cell math, and the preview all measure in the same units.
- A detach reports both objects it wrote — the one the region left and the one it became — so no caller is left rebuilding one half and drawing the other from stale geometry.
- One press commits at most one operation, and a press with no tracked move commits exactly a 1×1×1 box, because the corner cell never left the anchor cell. A press on a source mesh commits none: it leaves the selection at `{ kind: 'none' }`, so `commit()` finds no box to act on.
- A commit follows the active tool, with one exception: every verb a press can commit is the session's `activeTool`, one of the four box tools, and `detach` — the other value of `CommitVerb` — is supplied only by the `detachSelection()` command, so a detach is never reachable from a press and can never be left armed for the next one.
- A source-mesh hit is never treated as a cell anywhere: it only makes its object active, and it clears the selection and the overlay instead of inventing a region for an object that has no payload yet.
- Middle and right buttons never start an edit and never alter navigation state.
- A left press with no gizmo handle under the pointer always reaches this tool, so cell selection works while the gizmo is attached to the active object: `getGizmoBusy()` is the only claim test, and it is false whenever no drag is running and no handle is hovered. Pointer capture is never read as a claim — `TransformControls` sets it on every press, hit or miss.
- Every `picker.pick` call resolves `getCamera()` and passes that result, and the closure always names the app-owned viewport camera, so a pick uses the camera the editor navigates. No camera instance is cached, so a pick made after a camera move uses the moved camera.
- The session selection always names an object the pick hit, with the kind `session.ts` accepts for that object's representation.
- A hover never writes: the preview reads the region through `visitRegion` — ending the walk at its own cell limit —
  and reports nothing to the document, the selection, or the history.
- The preview is drawn from the same shape builder as the commit, so what a hover marks is what a press acts on at the
  same cell, at the same wall height, out of the same face.
- The color written by the `add` and `paint` commits is always `session.editColor`; this file defines no color of its own and never writes `maskColor`.
- Between pointerdown and pointerup no voxel data changes: only the overlay updates, and nothing outside the drag's own preview touches project or session.
- After `dispose()` no listener remains on `dom` or `window`.

## Errors
- There is no `Result` union: this is presentation-layer code. A successful operation is visible in the mirror and the selection; a failed one is logged to the console by `settle` and otherwise ignored.
- A `RangeError` from ring 0 is a programmer error and is not caught here: `cellOfLocal` and `dragBox` hold every corner — plane-derived and stepped alike — inside the packed `[-512, 511]` cell key space, so this file cannot itself produce a box outside it.
- A pick with no hit is not an error: it clears the selection. A cell hit whose raycast reported no face is not one either: its `normal` is `undefined` and the drag takes the camera's view direction for its plane.
- An `object`-mode press activates the object under the pointer and nothing else: no cell selection is set, no drag is armed, and no voxel is written, however the tool row is set. Mode is the whole of that rule, and the tool row only matters in `edit` mode.
- Pressing a box-consuming tool on an object that carries no uniform payload (`select`, `add`, `paint`, `remove`) is not an error either: the object becomes active and no drag is armed, because `armDrag` needs the object's grid to address cells and `project.get(id)?.uniform` is `undefined` for a group and for an import with no voxel payload — so there are no cells to address; the press then commits nothing. An object whose grid is merely empty cannot be reached this way at all: a `'cell'` hit needs an instance the mirror drew. A commanded `detachSelection()` on an empty selection is the same kind of not-an-error: the commit returns before it does anything, and nothing is logged. Pressing a raw source mesh is the same kind of not-an-error: the object becomes active, there is no selection kind to set, and no tool acts on it.

## Dependencies
- `../document/project.ts` — `Project`, `ObjectId` for the ids `onProjectChange` carries, `worldMatrix`, `get`.
- `./history.ts` — `EditHistory` (type only), the stack a press records one step in; `./session.ts` — `EditorSession`, `Selection`, `ActiveTool`, `SelectionShape`; `./ops.ts` — `addRegion`, `removeRegion`, `paintRegion`, `detachSelection`, `OpResult`; `../voxels/uniform/region.ts` — `regionBounds` and `RegionShape` (type only); `../voxels/uniform/grid.ts` — `HexColor` and `IntBox3` (types only).
- `../three-runtime/picking.ts` — `Picker` and `PickHit` (the `'cell'` variant is what `armDrag` consumes); its single `pick` method takes the `camera` argument, which this file supplies per call from `getCamera()`. `../three-runtime/overlay.ts` — `Overlay`: `showBox` and `clear` for the committed region, `showCells` and `hideCells` for the hover preview.
- `../voxels/uniform/grid.ts` — `KEY_MIN`/`KEY_MAX` for the key space `cellOfLocal` and `holdCell` hold a cell inside, `normalizeBox` for `dragBox`, and `IntBox3` as its return type.
- `three` — `PerspectiveCamera` as the `getCamera()` return type, `Vector2`/`Vector3` for NDC and cell math, `Matrix4` for world matrices and the world-to-local inverse, `Matrix3` for the normal matrix, `Plane` for the drag plane, `Raycaster` for its intersection.
Not imported: `three-runtime/controls.ts`. The gizmo and `OrbitControls` are wired in `app/main.ts`, which hands this file the gizmo's claim as the `getGizmoBusy` closure; this file only asks that closure (see Open questions).

## Tests
`tests/pointer.test.ts` drives the tool's own listeners with pointer events and answers picks from a variable, against a real `Project` + `EditorSession` and a 2×2×2 block, pinning both ends of a box drag — the cell a face hit names, and a box carried off the model into empty cells — and the `add` tool's own layer: one cell out of the pressed face on a click, the wall on a tracked drag, and `paint`'s box left on the seen cells. The rest is app-verified (README section 10), and the checks are manual and observable: drag a box and confirm the committed extents are the ones the preview drew, click once and confirm a single cell changes, drag across two objects and confirm the box stays in the anchor object, press `add` on a face and confirm a cell appears in front of it while the pressed cell keeps its color, drag `add` off the model and confirm the cells appear where the pointer went — in the layer in front of the pressed face, in the object's own frame — set `Add wall` above one and confirm the same drag builds that many layers while a click still adds one, press `paint` on a face and confirm it recolors the cell the user sees rather than stepping out of it, drag the gizmo and confirm no voxels change while the transform does, and middle/right drag to confirm only the camera moves. With the gizmo attached — the default `select` state for an active object — a click on a cell must select it, moving the HUD's selection readout and the overlay to the picked cell and leaving the transform alone; only a press on a handle may move the object. Then re-aim the viewport and click an object: the hit must be the cell under the pointer in that view, which is the per-pick camera lookup. A fresh import is the raw-mesh walk: before any voxelization a click must select the imported object — the object list and the HUD follow, no selection or overlay appears, and no voxel changes — hovering must change nothing at all, ticking `Show raw meshes` must bring the meshes back over the voxels once the object has been voxelized, and clicks must then act on the voxel surface in front of them, not on the mesh behind them.

## Open questions
- The gizmo's claim arrives here as the `getGizmoBusy` closure (`ViewportControls.gizmoBusy()` in `app/main.ts`), so `pointer.ts` still imports nothing from `three-runtime/controls.ts`. The closure is captured at construction, which is correct only because the composition root builds `controls` before it builds `pointer`.
