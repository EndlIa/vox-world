# src/three-runtime/controls.ts

Ring: 2 · Layer: three-runtime · Depends on: `three`, `three/addons/controls/OrbitControls.js`, `three/addons/controls/TransformControls.js`

## Responsibility

One object owning the viewport's navigation and the edit gizmo: it reads no voxel data, writes nothing to the document, and never renders. Navigation follows the camera it was built with, oriented by that camera's `up`, which in this world is `+Z`.

## Public interface
```ts
type GizmoMode = 'translate' | 'rotate';   // one handle set; three draws one per instance, and a subject may be given two
class ViewportControls {
  constructor(domElement: HTMLElement, camera: THREE.PerspectiveCamera);
  readonly orbit: OrbitControls;
  attachGizmo(object: THREE.Object3D, modes: readonly GizmoMode[], pivot: THREE.Vector3): void;
  detachGizmo(): void;
  gizmoBusy(): boolean;                                // true while a handle set owns the pointer
  onGizmoChange(cb: (matrix: THREE.Matrix4) => void): void;   // the node matrix the drag derives
  onGizmoCommit(cb: (matrix: THREE.Matrix4) => void): void;   // pointer-up: the matrix to write back
  setViewFrom(position: THREE.Vector3, quaternion: THREE.Quaternion, target?: THREE.Vector3): void;   // points the viewport at a pose, at the pivot it is given
  update(): void;
  dispose(): void;
}
```

## Internal logic
1. Constructor: `new OrbitControls(camera, domElement)` with `mouseButtons = { LEFT: null, MIDDLE: THREE.MOUSE.ROTATE, RIGHT: THREE.MOUSE.PAN }`. Wheel zoom keeps working through OrbitControls' own wheel handler, and left-drag stays free for the box tool. Damping is enabled, so `update()` must be called once per frame. `OrbitControls` captures the camera's `up` as its orbit axis in that same constructor, so which way is up is whatever the caller set on the camera before this point — this world is Z-up, and `src/app/main.ts` sets `camera.up = (0, 0, 1)` before building these controls, because the axis cannot be changed after construction. The controls always navigate the **viewport** camera they were constructed with: navigation is the editor's camera, and a clip or a field is what moves the output camera.
2. One `TransformControls(camera, domElement)` per handle set — three draws exactly one mode per instance, so a set is one instance of it — built in the constructor instead of on first use: an unattached set is inert (three's `pointerHover` and `pointerDown` both return while `object` is `undefined`), so having both ready costs a session nothing it would notice and no caller has to handle a set that does not exist yet. Each set takes the size and the colours `GIZMO_SIZE` and `GIZMO_COLORS` name — the rings drawn outside the arrows, without separating the sets' *pickers* (see 8), in hues toned for the dark viewport rather than three's fully saturated red, green and blue, with the handle under the pointer going white rather than three's yellow because yellow-gold is already this app's colour for the selection outline — and the same three callbacks; its mode is its identity. `attachGizmo(object, modes, pivot)` gives that object the sets `modes` names and takes every other set out of the scene, helper and all: one subject is attached at a time, the proxy is shared, and a set left attached would keep drawing handles for a subject that has none. Each attached set's helper goes into the scene that owns `object` — the root found by walking `object.parent` upward, where a root that is not a `THREE.Scene` throws `TypeError`, because an unattached helper would be invisible. Attaching also records `object` as the attached node and places the pivot proxy: one reusable empty `Object3D`, added to that **scene root** rather than to the object, at `object.matrixWorld · T(pivot)` — the object's own rotation and scale included, so a `local`-space gesture is oriented like the object. Every handle of an attached set, and the set's own raycaster with it, is put on layer 1 — the overlay layer `overlay.md` also states — so the picker's raycaster and the export camera, which both test layer 0, can neither pick nor capture a handle, while the gizmo still reads the pointer. The gizmo is attached to the proxy and never to the node: `TransformControls` draws its handles at the attached object's own origin and writes a drag into that object's own transform, so attaching the node would draw the handles at the node origin — the payload's min corner.
   The proxy is deliberately a sibling of the object and not its child: a child proxy would be carried along by the very motion a drag asks for, and because `TransformControls` measures its drag against the attached object's parent, the object would run away from the pointer at twice the rate. A scene-level proxy is also what keeps the handles under the pointer while the object moves beneath them.
3. That mapping is a world-space delta (see 5), so where the pivot sits inside the object changes only where the handles are drawn: a `translate` gesture takes the node exactly where the pointer went, and `rotate`/`scale` would turn and grow it about the content center instead of about the node origin. The attached node's own transform is never written here; the change callback is what carries the matrix out, and the caller applies it.
4. Live drag: the gizmo's `objectChange` event calls the change callback with the matrix the drag asks the node to take, and `dragging-changed` disables `orbit` while the pointer is down and re-enables it on release, so navigation never fights the gizmo. The `true` edge of `dragging-changed` also records the drag's reference frame — the node's world matrix and the proxy's, at the moment the gesture starts — so a drag is measured from where it began, not from the last frame.
5. The reported matrix is `pivotNow · pivotStart⁻¹ · nodeStart`: the delta `pivotNow · pivotStart⁻¹` is what the pointer did to the pivot in world space, composed with the node matrix the drag started from. The pivot's own local offset cancels out of that delta, which is what makes the derivation mode-agnostic — no mode is special-cased, and a node that is rotated or scaled keeps its rotation and scale while its position moves in world space. The pivot's world matrix is refreshed before it is read, because `TransformControls` applies a drag from `pointerMove` and dispatches `objectChange` without refreshing a world matrix itself.
6. Commit: the gizmo's `mouseUp` event calls the commit callback with that same matrix, and that is the one moment the caller writes the document. The matrix is handed over rather than read back out of the node, because the node is not what the gizmo moved; and the caller applies the same matrix to the scene during the drag, so the release only moves the write from the mirror to the document and nothing on screen moves. A drag that ends where it started still commits, with the matrix the node already had. The reference frame starts at the node's own world matrix, so a pointer-up that is not a drag reports the node unchanged rather than a stale gesture.
7. `gizmoBusy()` answers whether a handle set owns the pointer: `true` while any attached set has `TransformControls.dragging` set, or an `axis` that is not `null` — the handle the pointer rests on, which three's own `pointerHover` writes on every `pointermove` and clears to `null` when no handle is under the pointer. It is `false` when nothing is attached (`detachGizmo` clears `axis` too) and for a set that is `enabled === false`. This is the claim test the pointer layer is given, because capture is *not* one: three's `onPointerDown` calls `setPointerCapture` on the shared element on **every** press, hit or miss, so a captured pointer says nothing about which layer owns the gesture. A press over a handle is already visible here before the press is handled, since `axis` is set by the hover that preceded it.
10. `setViewFrom(position, quaternion, target?)` points the viewport at a pose, which is what the app's `View -> Camera` means and what its paused-frame handoff uses: it copies the pose onto `orbit.object` — the camera navigation drives — takes the radius navigation already orbits from (`max(orbit.object.position.distanceTo(orbit.target), MIN_ORBIT_RADIUS)`, so a viewport sitting on its own pivot still gets a usable one), puts `orbit.target` where the view is aimed, calls `orbit.object.lookAt(orbit.target)`, and then `orbit.update()`. That `lookAt` reads the camera's `up` at call time, so the restored viewpoint is oriented for this world's Z-up frame the same way navigation is — no axis is written here. Without a `target` the pivot is derived from the pose — the point it looks along, `position + forward · radius` (forward being `(0, 0, -1)` rotated by the quaternion) — and with one the pivot is that point verbatim, because restoring a view means restoring exactly where it was aimed rather than a point straight ahead of it. The `lookAt` is what makes the result an orbit pose rather than an arbitrary one — a bank the pose carries is not representable, so it is dropped — and `update()` rebuilds the offset and zoom state orbits and dollies work from, so the first orbit after the jump behaves like any other. It is the only path in this file that sets a camera pose directly rather than through user input, and it writes no project state, no document, and no flag; the pose and the target it is handed are plain vectors the caller owns, so it reads no document state either.
8. One press belongs to one handle set. Two sets can both find a handle under the same press: the rotate pickers are tori of radius 0.4–0.6 gizmo units and the translate pickers are cones reaching 0.6, so at the sizes `GIZMO_SIZE` gives them — 0.48–0.72 and 0.51 — a press just inside an arrowhead is inside a ring's band as well. Each instance raycasts its own pickers and starts its own drag, so that press would otherwise drag both — and since both drag the one pivot proxy, the gesture would both move and turn the node. The rule is therefore on the drag, not on the hover: the first set to start keeps the gesture, and a set that starts while another is already `dragging` is put back down on its own `dragging-changed` edge — `dragging` false and `axis` null — before its drag has produced anything. Which set starts first is `GIZMO_MODES` order, because that is the order the sets are built and so the order their own press listeners were added in. Three consequences of the placement: the loser applies no `pointerMove` (its `dragging` is false), it dispatches no `mouseUp` on release (`pointerUp` requires `dragging` **and** a non-null `axis`), so a gesture writes the document once even from the overlap; and the loser's hover goes down with its drag, because a set that may not act must not report a handle either. This is deliberately *not* read from hover state: three's own `pointerUp` clears `axis` on every set, so a press that follows a release with no intervening `pointermove` has no hover to read at all, and a ruling made there would silently stop applying — which is also why `handleSetDragging` is registered ahead of `handleDraggingChanged` on each set: the app's own handler must see the losing set already down, or the orbit would be re-enabled in the middle of the winning drag.
11. `onGizmoChange` and `onGizmoCommit` each fill one slot; the last registration wins, since the composition root wires them once at startup. `detachGizmo()` detaches every set, removes their helpers, and is a no-op when nothing is attached.
12. `dispose()` removes the `dragging-changed` backstop from every set, detaches them, removes their helpers, removes every other listener it added to them (the orbit `change` listener included), clears the registered orbit callbacks, and disposes the sets and both control objects, leaving the `domElement` as it found it.

## Invariants
- Navigation uses the middle and right mouse buttons only; `OrbitControls` never consumes a left-drag.
- Navigation moves exactly one camera, the viewport camera it was constructed with. `ViewportControls` writes nothing into the document and never renders.
- `setViewFrom` keeps the viewport an orbit camera rather than an arbitrary one: it moves the camera onto the pose and puts the pivot where the pose is aimed — derived from the pose when no `target` is given, and taken verbatim when one is, because a restore has to land on exactly the aim it left — so a bank the pose carries is dropped (it cannot be expressed) and the first orbit after the jump starts where the jump left off, at the radius the navigation already used. It reads and writes nothing the app owns: no document, no project, no flag, and the pose and target it is handed are the caller's own vectors.
- Exactly one document write per gizmo gesture, on pointer-up. The change callback fires many times per gesture and
  writes no document: it is the live path, and the commit is the same matrix once the pointer is up.
- The gizmo is attached to the pivot proxy and the node is never dragged by it: the change callback carries the matrix the
  gesture asks for and the commit callback carries the same one, so a caller may apply it live, ignore it entirely, or
  apply it only on release, and in every case one gesture ends with either the whole transform or nothing.
- The proxy is a child of the scene, at the pivot, and of nothing else: `attachGizmo` re-places it, `detachGizmo` takes
  it out of the graph, and no attachment leaves more than one. Nothing is ever added under the attached object, which is
  what keeps the handles under the pointer while that object moves.
- A drag is measured from the reference frame the `dragging-changed` edge recorded: the reported matrix is
  `pivotNow · pivotStart⁻¹ · nodeStart`, which contains the whole gesture, and never an accumulation of per-move deltas.
- The pivot is presentation only: it decides where the handles are drawn and what a `rotate`/`scale` gesture turns about,
  and `translate` takes the node wherever the pointer went whatever the pivot is. Because the delta cancels the pivot
  out, a drag can never be amplified by the pivot being far from the node origin.
- `gizmoBusy()` is `true` exactly while a handle set owns the pointer — a drag in progress, or a handle under the pointer — and `false` after `detachGizmo`, and for a set that is disabled. It never reads pointer capture: `TransformControls` captures the pointer on every press regardless of what it hit, so capture cannot separate a gizmo gesture from a tool gesture.
- One press belongs to one handle set: the first set to start keeps the gesture and any other set that starts off the same press is put back down before its drag produces anything, so a press in the band where the two sets' handles overlap yields one set's transform — never a move and a turn at once — and exactly one commit.
- A set is created once and never re-moded or replaced while the controls live: a subject's sets are chosen per attach, and a set the subject does not name is detached rather than disposed, so its handles cost nothing while it is out of the scene.
- A left press with `gizmoBusy()` false is the active tool's, so a click on empty space still selects while the gizmo is attached; only a press that starts or continues on a handle is the gizmo's.
- `update()` before `attachGizmo()` is legal and only advances navigation.

## Errors
- `attachGizmo` throws `TypeError` when the object's root is not a `THREE.Scene`.
- `attachGizmo` takes the pivot verbatim: it is a local-space point, neither validated nor clamped, so a caller that hands
  over a non-finite one gets handles it cannot reach. What it is given in practice comes from content bounds, which are
  finite or the origin.
- `detachGizmo()`, `onGizmoChange`, and `onGizmoCommit` before any attachment are no-ops; interactively so, never silently wrong, because no change can be produced without an attached object.
- `gizmoBusy()` throws nothing and is legal at any time, including before any attachment: no attachment, and a disabled set, both answer `false`. The sets themselves exist from construction, so no caller has to ask whether one does.

## Dependencies
- `three` — `PerspectiveCamera`, `Object3D`, `Vector3`, `Matrix4`, `MOUSE`.
- `three/addons/controls/OrbitControls.js` — viewport navigation (README §3 addon map). Its orbit axis is the camera's `up`, captured once in its constructor, so the caller's choice of up reaches navigation through the camera alone.
- `three/addons/controls/TransformControls.js` — the edit gizmo; neither is re-implemented. One instance per handle set, because three draws one mode per instance. Its `dragging` and `axis` state is what `gizmoBusy()` reads and what the press ruling reads and writes, and its `setColors` is the only styling it is given.
No outer-ring import: no editor session, no document, no UI.

## Tests
- No vitest file: both classes need a DOM element and pointer events, which the node test environment does not provide. Verified by running the app (README §10): middle/right navigation with left-drag free, one commit per gesture, and navigation that drives the viewport camera alone — the authored camera moves only through an explicit command: `View -> Camera`, a pose field, or a carrier drag. Gesture ownership is checked in the same walk: with a `select` gizmo attached to the active object, a left click on a voxel must reach the tool and select the cell under the pointer, while a press that starts on a handle must move the object and change no voxels.
- The commit contract is instead pinned where it is observable: the tool layer that consumes `onGizmoCommit` writes the
  document once per drag.
- `setViewFrom` has no vitest coverage either, for the same DOM reason; it is verified in the app walk: pressing `View -> Camera` must put the viewport on the authored pose and write nothing — the `Camera` group's numeric fields and an exported frame are unchanged — and a middle-drag afterwards must orbit that shot rather than jump, with an authored bank arriving dropped because an orbit camera cannot represent it. The optional `target` is walked by the playback handoff: the view a pause hands over, and the view a non-looping end puts back, must be aimed exactly where the run started aiming, with the document untouched.
- The pivot, the mapping, and the live path were verified by running the app on the boot demo cube, measured
  on screenshots: with a content-center pivot the handles are drawn over the middle of the cube — the Z handle hidden
  inside it — while the same build handed a zero pivot draws them at the payload's min corner, which is the old
  behaviour; while the button is still down, the cube has already moved and sits exactly where it lands after the
  release, which is what rules out the running-away-at-twice-the-rate failure a child proxy would produce; dragging the X
  handle 120 px right commits `-1.000` → `-0.207` on `position.x` with `y` and `z` untouched, as a timeline `position`
  keyframe readout shows; and the handles move with the cube across that commit, which is the rebuild re-attachment of
  `main`'s loop rather than a frozen helper.
- The two sets and the press ruling were verified the same way, on the boot cube with nothing else touched. Both sets are
  drawn at once around the content center — arrows and rings together, no mode control anywhere, and the `Camera` group's mode
  button disabled — and the carrier takes one set: selecting it leaves the arrows alone drawn, and a mode it was left in does not
  reach an object, which shows its rings either way. The band was found by measurement rather than by eye: with the pointer
  resting on it a handle of each set highlights at once, and a press there is the one place the ruling can matter. Pressing there
  and dragging a whole cell moved the cube to the next cell with its orientation unchanged, and one `Ctrl+Z` restored the frame
  pixel-for-pixel, so that gesture was one write and one history step; the same press with the ruling disabled instead left the
  cube moved **and** turned, which is the composition the ruling exists to prevent. The scenario that exposed the hover basis is
  walked too: a bare press-and-release on that same point — a drag that ends where it began, which writes nothing — clears the
  hover three tracks, and a press immediately after it, with no `pointermove` in between, still produced a move alone and one
  `Ctrl+Z` still restored the frame exactly. A drag on a ring elsewhere must turn the object about its content center with its
  position unmoved and the shot's fields untouched, and a drag on an arrow must move it with its orientation unmoved.

## Open questions
- Which set wins a press that lands in the overlap band is the first in `GIZMO_MODES` order — `translate` — which is a guess about what a press there meant: the band sits just inside each arrowhead, so a press aimed at a ring in it moves the object instead, and nothing on screen says which way the press will go. A priority a caller could name per subject, or the losing set's handles drawn dimmed under the pointer, would make the choice visible.
- The ruling is not a picking decision — it lets both sets' `pointerDown` run and takes the gesture away from all but the first — so it depends on three's `dragging-changed`/`mouseUp` sequencing rather than on a single pick, as `TransformControls` gives no hook between its own hover and its drag. A future three that started a drag without that edge, or dispatched `mouseUp` for a set it never dragged, would need this re-made — the assertions to keep are that the losing set applies no `pointerMove` and dispatches no `mouseUp`.
- The orbit pivot is one shared value and nothing ever centres it on the scene: the app leaves it at the world origin, and `View -> Camera` moves it to the point the pose looks along. A `setOrbitPivot(point)` member, or a pivot derived from the mirrored bounds, would let navigation in a scene far from the origin orbit that content instead of empty space.
- No shared constant fixes the overlay layer; layer 1 is stated here and in `overlay.md`, and both files must keep it equal.
- The interface exposes no query for "a gizmo is attached" distinct from `gizmoBusy()`; the pointer layer needs only the latter, and reads the document write through the `onGizmoChange`/`onGizmoCommit` slots, so no further gizmo state leaks out.
